## Findings — G1/G2: 3D requests are five distinct problems, not one “make it 3D” prompt

1. **Input type and hidden surfaces.** `[D]` Meshy separates text-to-3D (D05), single image-to-3D (D06), dedicated **multi-image** input (D07), and retexturing an *existing model* (D08). D07 accepts **one to four separately supplied input views of the same object from different angles**, differentiates geometry views from texture-only references and has topology/remesh controls; photos provide evidence of the real back, while generated views remain hypotheses. Both D06 and D07 can expose optional `texture_prompt` for the **texturing phase**, not free-text geometry instruction. D06's returned four-view thumbnails, where supplied, are *outputs/previews*, not four separate source photographs. `[O]` A TRELLIS.2 issue author requests multiple images because the unseen back is messy (O19); a Hunyuan3D-2.1 issue reports multi-view failure with a particular default-model setup (O20). Neither issue negates D07's supported Meshy endpoint or establishes that the named GitHub model universally works/does not work with multi-image inputs. `[D]` The upstream READMEs D10–D11 are the check on what their projects actually document. `[N]` “front view + real rear view” is a different evidence condition from writing “accurate back” under a single front screenshot.
2. **Shape, mesh and surface appearance separate.** `[D]` D08 accepts a supplied mesh for retexture, and retaining existing UVs is a separate setting; this does not transform texture into geometry. D05/D07 expose non-text outputs/settings beyond the description. `[R]` 3DGen-Bench (R01) and 3D Arena (R02) study human preference/evaluation under their own procedures, not proof of printability, watertightness, scale, good UV seams or animation-ready topology; R02 explicitly distinguishes perceptual appeal from real-world utility. `[N]` Silhouette, rear/underside, non-manifold edges, normals, UVs, material maps, print constraints and export scale are **different inspection questions**. An appealing turntable can fail any of them; no study above evaluated the student's or a future user's asset against those gates.
3. **Consistency under edits is a different task from creating a new asset.** `[R]` EditP23 (R03) conditions its research pipeline on a *pair of original and user-edited image views* to propagate a 3D edit, rather than claiming any text instruction alone will keep all angles coherent. `[O]` An older stable-dreamfusion issue describes a Janus/multi-face failure in a different pipeline (O22); a Hacker News commenter reports arbitrary-image TRELLIS.2 outputs worse than polished examples (O21). The older model symptom and an uncontrolled demo comparison identify risks, not a performance rate for modern tools. `[N]` A request to “change only the fabric on this chair from every angle” has different reference and QA needs from “make a new chair.”
4. **Vendor examples are bounded.** `[D]` Tripo's input tips (D09) describe preparation for its own image-to-3D workflow, not transferable Meshy API flags. `[O]` Requests and bug reports O19–O21 are individual contexts; the pages do not verify the original image set, model settings or recovered mesh. Public indexed Reddit leads about game assets and printed detail were inaccessible and were **not** used to supply missing observed cases (see uncertainty section).

## Findings — G3: “enhance this photo” crosses conservative and imaginative operations

1. **Promptable model versus settings-only operation.** `[D]` Photoshop's current Generative Fill page (D14) documents an active selection, text prompt **or blank fill**, model selection and variations. Gigapixel's documentation (D12) is more conditional: Recover v2 has a Detail setting; Redefine **realistic at Subtle** can expose an *Image description*, while Redefine **creative** has an *Image description* plus creativity/texture controls. The vendor says Redefine's text should describe the image, rather than issue a “change X” command; it says Face Recovery is disabled in Redefine creative. Face Recovery itself (D13) offers face selection/strength and Realistic/Creative modes, **not a Face Recovery prompt box**. Lightroom Classic's Enhance Details (D15) is an image-processing workflow, not a generative repaint instruction. `[N]` A single sentence formatted as a prompt cannot be pasted interchangeably into these four different workflows.
2. **Selection and seams.** `[O]` Photoshop community posters describe a visible Generative Expand boundary (O10), a patch darker than its surroundings (O11), and a different failure where Generate does nothing or enhances an object instead of removing it (O12). The last discussion includes a community expert pointing to the *Remove* tool for removal; it is not evidence for the separate phenomenon of changes outside a selection. That spill complaint is **HELD** S012 S13, not a fourth new report. `[D]` D14 documents selection as an operation, **not pixel-identical preservation** outside it. `[N]` Selection, correct operation and a feather/color/edge comparison answer different problems; adding “seamless” to the prompt does not certify a clean composite.
3. **Human faces, fabrics, and invented detail.** `[D]` D13 itself acknowledges that reconstruction can slightly change expressions and smooth hair or small facial features; its creative mode can synthesize missing detail. `[O]` Users report a need to choose faces individually (O13), wish for reference-guided upscaling as a **request rather than an existing feature** (O14), fabric banding on mild denoise (O15), oversharpening (O16), invented facial hair (O17), and subjective differences between recovery modes (O18). These are nonrepresentative single-thread observations; they do not show that turning a slider or describing a face will recover historical identity. `[N]` Readable small text, architectural dimensions and original identity remain unknown when the source lacks the pixels; compare a restored version to the original rather than to another generated image alone.

## Findings — G4: an architectural visual can obey the mood and change the design

1. **Text, model view, style and layout are not one instruction.** `[D]` SketchUp's prompt, preset and custom-prompt documentation describe text and separate style inputs (D01–D03). BFL's building guide (D18) covers descriptive prompts; its layout use case (D19) uses referenced images with editing instructions and warns that exact pixel-level layout fidelity should not be expected. D19 does **not** describe a generic native ControlNet upload in that workflow. Midjourney's Style Reference (D16) transfers aesthetic character, **not** the objects/people from that reference; its Version page (D17) makes syntax/model behavior version-dependent. HELD S012 P08 explicitly distinguishes inspiration from precision editing; HELD S013 E06 documents edit-mode operations separately. `[N]` “Use image A for geometry, image B for color/material mood” specifies roles for a compatible interface; the words do not create two input slots or lock a bay grid.
2. **Detail/geometry drift is not just an ugly result.** `[O]` SketchUp participants report malformed furniture (O01), formerly straight model lines becoming crooked (O02), differing render behavior after an update despite similar settings (O03), unexpected material (O06), and lighting/surface mismatch (O07). A later user asks for historically removed geometry-respect controls to return (O05); old slider names are **not a current-UI recipe**. `[D/O]` In a separate 2026 forum exchange (O04), SketchUp staff distinguishes **Erase** (masked source is excluded from context) from **Paint** (source context retained) while a user wrestles with changes. This is a product-specific explanation, not a guarantee that either mode retains CAD geometry. `[N]` Bay count, column position, roof outline, finish, light direction and camera framing require separate checks if important.
3. **Fidelity competes with presentation.** `[O]` A practitioner says clients read speculative render colors as already-selected finishes (O08); a public SketchUp discussion contains differing professional attitudes about AI assistance versus knowing lighting/material/render methods (O09). The thread is not a poll of the profession. `[R]` HELD S013 E09 found clutter could contaminate facade-edge guidance in a bounded architectural study, and HELD E08 distinguishes edit adherence from preservation outside an edit in its benchmark. `[N]` A polished concept can plausibly communicate *more decisions than were made*; verbal instructions alone cannot turn a schematic render into a measured facade, approved finish schedule or verified site image.

## Cross-source control map — what the text does not replace
| Problem in a future task | Documented input/control rather than an interchangeable magic phrase | What the reports or research leave unresolved |
|---|---|---|
| Preserve architecture while changing atmosphere | Existing view/layout reference; localized editor/mask where available; style and version controls (D01–D03,D16–D19; HELD S013 E06) | O01–O07 describe drift; old SketchUp geometry sliders not necessarily present; no exact-view guarantee. |
| Get a usable back of a 3D object | **Separately supplied** alternate-angle source images through an interface that accepts them, e.g. D07; photographed backs evidence a real back, generated views do not | O19–O21 express failure/frustration in other tools; D06 thumbnails are outputs, not extra input evidence. |
| Refinish an existing mesh | Existing-model retexture + material/UV settings (D08) | The text “keep same UVs” is not proof that UVs, material seams or geometry survive export. |
| Repair photo region | Correct operation: selected Generative Fill/blank prompt/Remove tool; tonal/manual compositing as separate edit (D14,O10–O12) | Pixel spill and seams may remain; HELD S012 S13 is the selection-spill report. |
| Improve an old face without fabrication | Face selection/strength/model choice (D13), or separate descriptive Redefine text only where D12 exposes it | O13–O18 are person-specific; unrecorded facial details cannot be authenticated. |
| Compare 3D outputs | Tested source-view fit, multiview geometry and task-specific mesh checks in addition to visual appeal (R01,R02) | Preference datasets do not establish CAD accuracy, printability, retopology quality or downstream suitability. |

## Conflicts, uncertainty and access
- **Supported multiview vs requests for it:** Meshy's dedicated endpoint D07 **does** take multiple supplied geometry views (real photos or eligible generated images, which do not verify a real rear surface); O19 requests such support in TRELLIS.2 and O20 reports a Hunyuan default-model failure. They are not contradictory descriptions of the same API. D06 output thumbnails must not be counted as user-supplied multiview inputs.
- **“Keep exactly the same” vs guided edits:** D14 documents selected filling; HELD S012 S13 and new O10–O12 describe different failure modes. D19 warns against pixel-exact layout matching; D16 style refers to appearance. The statements concern capability, failure reports and guarantees respectively; they cannot be averaged into a success rate.
- **Restoration fidelity vs creative detail:** Topaz's D12 provides an actual promptable *Image description* **only in specified Redefine configurations**, whereas D13 face recovery is selection/strength/mode. O17/O18 describe identity concerns. Neither the mode label “Realistic” nor prompt adjectives verify the original person's appearance.
- **Social-platform coverage gap — Reddit:** Four direct Reddit threads, old/JSON/API endpoints and a reader gateway returned 403/security blocks. Search-index snippets gave leads in the source register but **zero Reddit discussions were directly read, counted or used as evidence**. Twenty-two directly read human discussions from accessible product forums, GitHub issues and Hacker News satisfy the broad first-hand corpus, but cannot substitute for Reddit community perspectives. No `[STOCKPILE SHORTFALL]` on the total quotas; a **Reddit-specific coverage gap** remains.
- **[UNVERIFIED]** The actual account, UI version, image/model input, renderer, image-edit result, user permissions and course/client standard are unknown. None of these documents says a particular copy-paste sentence worked on the user's work; software documentation may have changed since access.
